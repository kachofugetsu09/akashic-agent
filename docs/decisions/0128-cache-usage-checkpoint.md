# 0128 · 缓存效率用量落可重建检查点，重启后只扫新增 Turn

- 状态：accepted / implemented for review
- 日期：2026-10-21
- 关联：#1375（缓存效率由 models 按需计算）、#1378（分批读取历史）、0127；参考 DSH `session-projection-cache` 的检查点

## 背景

`plugins/models/usage.py` 从消息账本切 Turn，再按 `call_record_id` 批量读 `model_calls`，得到每个 Session 来源已闭合 Turn 的累计量。
#1375 选择不建投影库，累计量只在进程内存里，重启后第一次打开从头扫。#1378 记录了这个代价：2.7 GB 生产库首次读取 139.7 秒，
分批后仍是 29 次请求、68 秒；每次部署重启都会重来，扫描期间在线程里占 GIL，也拖慢事件循环。

## 决定

1. 进程内状态不变，另由 models 在 `plugin-data/models-<市场>/cache-usage.sqlite3` 保存检查点：每个 Session 的 head、
   每个 (Session, 来源) 的消费位置、累计量、最近 50 轮，以及被动回答的输出 token。
2. 首次访问时恢复检查点；每次扫描后只写有变化的来源和 head，输出 token 只追加尚未写入的条目，被移除的 Session 整体删除。
   head 在同一事务里最后写。
3. 检查点是派生数据：
   - 版本不符或文件损坏时记警告、删除文件、从头重扫；写入失败只记日志，内存结果照常返回，下次再写；
   - 账本 head 小于检查点记录的 head（恢复备份或回退）时，整个 Session 在内存和检查点里一起丢掉、从头重算；
   - 某个来源的消费位置超过当前 head 时，这个来源重算，即使还没有闭合 Turn 也落盘，并在同一事务删除它的旧输出。
4. 检查点存的是按当前计数规则算好的结果。修改计数规则（什么算计入、主动来源集合、预览）必须把 `_CHECKPOINT_SCHEMA` 加一，
   旧结果随之丢弃重算；不加一就会一直沿用旧规则算出的历史。
5. 仍不加后台任务：打开页面时按原来的 2 秒预算推进；0127 的空闲预热最多推进一次预算，没有页面在看时停在当前进度。

## 结果

隔离副本（5,728 条消息，12 个计入 Turn）：重启后首次完整读取从 427ms 降到 13ms，结果与旧算法逐字节相同；
写入垃圾内容后重启，日志出现 `cache usage checkpoint discarded`，重扫后结果仍逐字节相同。

小实例：
- 发送新消息后轮数加一，重启后旧回答的"输出 N tokens"尾注仍在；
- 先备份账本、发一条消息让检查点前进，再停机换回备份：重启后结果与发送前、与删掉检查点全量重扫都逐字节相同，新回答的输出记录被清掉。

## 后果

- 收益：生产库的全量扫描只在首次升级时发生一次，之后每次重启只读新增消息。
- 代价：
  - 多一个可删除的派生文件；它不进模型注册库，也不参与模型备份；
  - 重启不再自动纠正：以前算错的结果重启即重算，现在要靠升 schema 或删除文件；
  - 账本没有实例身份，只靠 head 判断回退；换成另一份 head 不小于检查点的账本时检测不到，需要手动删除 `cache-usage.sqlite3`。
- 不做：把检查点并入 `model-registry.sqlite3`（那是有 revision 与备份的领域库）；后台常驻扫描。
