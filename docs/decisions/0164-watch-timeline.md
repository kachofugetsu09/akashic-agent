# 0164 值班：一条不删的时间线，反复开口的事写成嘱托

状态：proposed / implemented for review

## 背景

0162 上线后读了八个后台回合，又从机制上问了一个问题：用户连着很多天在同一种情形下让它做同一件事，哪天他没开口，它会不会自己做。答案是不会，原因不在提示词：

- 后台回合眼前的对话名义上是最近 72 小时，实际往回只读 800 条消息。主对话一天约 500 条（含工具调用），所以它只看得到最近一天多。同一句话用户说了三天，它从没在同一个视野里见过三次。
- 对话里每一行只有时间和原话，不带当时的状态。"他是到家之后说的"要拿值班记录的时间去对，没有人让它对。
- 事件全文和值班记录留十四天，足迹留三十天。更早的事没有任何地方查得到。
- 一件当场办完的小事不留任何痕迹，下一轮的它不知道这件事发生过。

把窗口放大到某个天数解决不了：周期比窗口长的习惯照样看不到。

另外，它新接的一个来源把同一件事交进来五次：来源给事件算标识时把一个会变的数算了进去。

## 决定

1. 系统记一条时间线 `watch/timeline/年-月.md`：用户对它说的每一句话、每一次状态变化，按时间排在一起，按月一个文件，只追加，不清理。用户说的每一行后面带上之前半小时内最近的一次状态变化，单独搜到这一行也看得出当时的情形。每次轻唤醒把上次以来新的部分追加进去；第一次往回补到账本和事件文件够得着的地方。
2. 现场说明里告诉它眼前只有最近一天，更早的到时间线里搜。眼前放多少仍由篇幅决定，能看多远由它查多远决定。
3. 每日复盘时，把用户这一天让它做的事挨个到时间线里搜：说过几回、每回之前刚发生了什么。已经说了好几回、每回都跟在同一种情形后面的，写一条长期嘱托，那种情形再出现时叫醒它，醒来直接办，办完告诉用户；只跟钟点有关的才按钟点定；只说过一两回的不算。用户说不用了就收掉。
4. 接来源的条件从"每回都有新的"放宽到"反复回去看的地方"，包括只是回去确认有没有变的。
5. 来源交的每条事件，标识只认这件事本身，会变的部分不算进去；接好之后连着试跑两次。值班记录里同一件事反复进来的，复盘时去修来源。

## 已知限制

- 时间线只记主对话里用户说的话和状态事件，不记它的回复和工具调用；要看这些仍然去账本。
- 当时的情形只取之前半小时内最近的一次状态变化。隔得更久、或者由几件事合起来才成立的情形，要它自己往上翻几行。
- 找出"同一件事说了好几回"靠它自己去搜，系统不替它归类。它不搜就看不到。
- 写成嘱托之后每次那种情形出现都会用掉一次叫醒额度。
- 首次补记要往回读几千条消息，只发生一次。
- 时间线不清理，一年约几千行。
