# 0149 · 值班（watch）取代 Wake：便宜模型看流，主 Agent 自己决定做什么

- 状态：proposed / implemented for review
- 日期：2026-11-11
- 关联条款：PRO-003、PRO-005、PRO-006、SEC-011、PLG-014、PLG-016、TST-001
- supersedes：0040、0049
- superseded by：无

## 背景

Wake 把"什么吵醒了 Agent"和"醒来能做什么"绑在一起：内容候选只能走初筛、分享、跳过三个专用工具，告警只能发通知。生产数据（2026-10-28 至 11-10）显示：

- 126 次内容唤醒里 95 次发了消息，明确跳过 11 次，醒来几乎等于开口。
- 语义兴趣分日均 0.03，十四天 1659 条内容没有一条超过 0.3，评分池实际由来源自带的预处理分驱动。
- 用户对论文类推送长期不接话，系统没有任何途径据此调整。

用户要的是：所有来源一视同仁；Agent 有自主性但不过度打扰；倾向随用户的反应调整；新增或移除一个来源足够简单。

## 决定

新增内置插件 `watch`，Wake 不再运行（预设里关闭，随后删除）。

1. **事件只有一种形状**：`id、source、at、title、text、url、state`，按到达日写进工作区 `watch/events/`。入口有三个，落在同一处：
   - `eventmail.stream.v1`：按信封序号增量读取现有来源交给 EventMail 的内容与告警，这些来源不用改。
   - `watch.events.v1`：插件直接交一件事。
   - `watch/sources/名字.jsonl`：任何程序追加一行就是一条事件；删掉文件就是移除来源。
2. **值班员**是插件自己驱动的小循环，跑在可配置的模型链上（按顺序退避），每个间隔把新事件攒成一批，给每条一个去向：`wake`、`inbox`、`log`。它没有会话、不说话，只有只读文件工具和 `decide`。模型失败或输出不合格就换链上的下一个；整条链失败时事件留在原处下次再判。
3. **叫醒主 Agent** 走 `programmatic.v1`：在一个内部会话里跑一轮默认回复程序，工具与普通对话相同。那里的文字不投递；要让用户看到，主 Agent 调用既有的 `message_push` 发到配置的主对话。每天叫醒次数有上限，超出的进待看列表。
4. **状态尽量是文件**：`WATCH.md`（主 Agent 写给值班员的嘱托）、`cases.md`（纠正）、`inbox.md`（待看）、`notes.md`（便签）、`log/`（值班记录）。嘱托每行带到期日，一次性嘱托触发后归档，到期不续归档；可以带查看时间，到点由值班员先看一眼。
5. **对话不落副本**：值班员和主 Agent 看到的"最近对话"每次从消息账本现查，主动消息带上用户有没有接话。
6. **闭环**：主 Agent 被叫醒时可以纠正值班员、改嘱托；每日复盘回看值班记录，更新记忆、整理嘱托与来源；用户来主对话聊天时，主 Agent 得到一行便签指针。

## 理由

- 值班员不进会话、不用回复程序：它每天要跑几十次，带上人格、技能和记忆材料的完整提示词对便宜模型又贵又慢，也用不上。
- 叫醒主 Agent 复用 `programmatic.v1` 而不是自建来源：它已经是"内部会话里跑完整一轮、正文不投递"的公开合同，恢复语义沿用 SEC-011。
- 状态（位置、睡眠、在线）没有另一条通道：来源在状态变化时交一条标了 `state` 的事件，"用户当前状态"就是各来源最近的那一条。没有选"值班另外去查各个状态提供方"：那样每多一种状态就多一处配置，状态的变化也不会留在值班记录里。也没有把 EventMail 的状态信封直接接进事件流：来源每次轮询都会写一个信封（生产实测每个来源每小时 12 个），状态有没有变只有来源自己知道，所以由来源在变化时经 `watch.events.v1` 交事件。
- 说话复用 `message_push`：不在主对话里跑模型，主对话的上下文不被后台工作污染。
- 没有选"实体图或向量共振做第 0 层"：生产数据已经否定了语义分；也没有选来源自带优先级：紧急与否看内容，不看来源。
- 没有给值班员保留评分池、attempt 表和选择结算：这些是为"固定三步流程"服务的。值班的记录是可读文件，足够回答"这条事件为什么是这个去向"。

接受的代价：

- 值班员直接读工作区 `memory/` 下的文件，依赖路径约定而不是合同；路径可配置。
- EventMail 里 Content 的选择、结算状态不再推进，条目停在 pending。EventMail 的瘦身另行处理。
- 文件来源按字节位置续读，要求只追加；截短后又长回原位置的文件可能漏读开头，不为此保存文件指纹。
- 叫醒主 Agent 的交接靠待看列表：被叫醒的事件同时记进待看，处理完由它删掉。回合失败或进程中断时事件还在待看里，但不会自动重跑那一轮。
- 主 Agent 在后台拥有与普通对话相同的工具，外部正文可能带指令。提示词要求把正文当材料，值班员没有外部动作；更细的授权边界留作后续。

## 影响

- 正面影响：新增来源只要会写一行 JSON；Agent 醒来可以选择沉默；判断依据可读可改。
- 兼容性：`wake` 的设置、评分和 Wake 技能不再使用；EventMail 的来源合同不变。
- 数据和迁移：不迁移 `wake.sqlite3`，保留在原处。首次接上事件流从当前序号开始，不回放历史。需要在设置里填写主对话，值班才运行。
- 失败与回滚：关闭 `watch`、重新启用 `wake` 即回到旧行为；两者不共享状态。

## 验收

- [x] `scripts/watch_scenario.py`：三种入口的事件都被判断，待看、嘱托归档、后台会话与主对话消息符合预期；模型链失败时游标不前进，恢复后补判。
- [x] 隔离实例加真实模型：命中嘱托叫醒主 Agent，它选择不发消息并留便签；用户来聊天时自然带出；每日复盘暂停了不可核实的来源并记下待告知。

## 何时重新考虑

- 值班模型的调用量随来源增长到免费额度之外，需要在模型之前加确定性的去重或合并。
- 需要多用户或多主对话时，嘱托与便签要按用户分开。
