# 0099 · Session 与 Models 账本采用 WAL NORMAL

- 状态：accepted。
- 日期：2026-10-09。
- 关联：STA-001～STA-003、CAP-002、SES-001～SES-002、ERR-001。

## 决定与理由

维护者确认采用进程崩溃级保证，以减少每次事务提交等待刷盘的成本。
MessageLog 与 ModelsStore 的写连接使用 WAL 和 `synchronous=NORMAL`。
事务仍原子提交，普通进程退出、SIGKILL 或容器崩溃不会撤回已提交事务。
宿主断电或操作系统崩溃后，最新提交可能丢失；checkpoint 按页数触发，
没有固定毫秒数或事务数的丢失上界。Docker Compose 和持久卷不增加刷盘保证。
语义依据见 [SQLite synchronous](https://sqlite.org/pragma.html#pragma_synchronous)。

┌───────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ 提交工具 started  │ →  │ 执行外部操作     │ →  │ 提交结果与回执   │
└───────────────────┘    └──────────────────┘    └──────────────────┘
          宿主故障可能丢失记录；已经发生的外部效果不撤回。

## 影响与恢复

Session 消息继续由 MessageLog 追加；工具、送达等 owner 状态仍按原事务协议更新。
Models 继续记录请求 intent、响应、usage 与配置，不改变任何 schema、记录身份或更新权限。
没有新增自动失效、裁切、物理删除或 GC；允许的主动数据管理仍由原 owner 和显式用户授权决定。

普通进程崩溃后，使用已提交消息和回执恢复，未结算工具仍执行原 query/幂等规则。
宿主故障可能丢失工具 start intent 或终态；恢复程序可能把已执行操作看成尚未执行。
维护者接受这项风险，此保证不覆盖宿主故障后的外部效果去重。
完整恢复只能依据实际保留的账本、外部服务记录或已有备份；不存在的记录不能伪造补齐。

曾考虑保留 FULL，或只在外部操作前启用强刷盘屏障。两者具有更强的宿主故障保证，
但继续承担逐提交或关键操作的刷盘等待；本次明确选择统一的 NORMAL。
若以后需要宿主故障后已确认消息不丢或可靠识别已开始外部操作，应重新批准更强屏障。

## 验收

使用临时数据库和真实子进程提交消息、owner intent、模型响应，
在写连接保持打开时 SIGKILL，再打开数据库比较完整记录、身份与顺序。
这验证普通进程崩溃恢复，不证明断电耐久性；不操作正式 workspace。
