# 0035 移动协议交付按变更性质分阶段

- 状态：accepted
- 日期：2026-08-13
- 关联条款：MOB-008、MOB-006、TST-007、GOV-002

## 背景

MOB-008 初版把"任何协议变更"压成同一种 core-first 交付顺序。评审指出：兼容新增不需要移动端同步就能保持旧客户端可用；能力门控新增依赖客户端 capability 声明；语义变更需要废弃窗口；只有 breaking removal 才要求双方同步。固定的 core-first 既不能区分这些围栏，"同一周期"也不是可验证的兼容边界。

## 决定

移动协议变更按四种性质选择交付阶段：

1. 兼容新增：core 先合，移动端同周期配套更新 pin 与消费代码；旧客户端不因未跟进而失败。
2. 能力门控新增：core 先合且必须带客户端 capability 声明；未声明能力的客户端不接收新事件；移动端配套 PR 声明能力后启用。
3. 语义变更与废弃期：core 先合并明确废弃窗口；窗口内新旧语义共存；窗口结束前不得单方面删除兼容路径。
4. Breaking removal：移动端配套 PR 必须先准备完成且固定组合 Gate 通过（包含旧消费声明的移除与新 pin），core 随后合并移除协议面，移动端再前进最终 pin 并合并。若移动端无法先准备配套，core 侧必须保留废弃期后再删，不得在移动端移除消费声明之前单方面删除协议面。

每个跨仓库变更在 PR 描述中声明所属阶段与理由；阶段判定有歧义时先讨论，不按最方便实现的顺序合并。

## 理由

交付顺序必须匹配变更对旧客户端的影响半径。兼容新增的影响半径是零，能力门控的半径是"声明了能力的客户端"，语义变更的半径是"废弃窗口内的消费者"，breaking removal 的半径是全部已发布客户端。用同一顺序覆盖四种半径，要么过度阻塞移动端（对兼容新增），要么让 breaking 变化失去同步围栏。

## 影响

- MOB-008 按四阶段重写。
- 现有协议 pin、runtime-contract lock 与跨仓库 Gate 机制不变，仍是每个阶段的验证证据。
- 历史 PR 不受追溯改写；今后跨仓库协议 PR 按本决策声明阶段。

## 验收

- 每个移动协议 PR 描述包含阶段、理由与两端引用。
- 兼容新增在移动端未跟进的旧 APK 上行为不变。
- 能力门控新增在未声明能力的客户端上不可见，不触发协议拒绝。
- 语义变更的废弃窗口在两端都有明确边界与删除条件。
- breaking removal 在移动端配套 PR 准备完成且固定组合 Gate 通过之前，core 不删除对应兼容路径；配套就绪后 core 先合、移动端前进最终 pin。
