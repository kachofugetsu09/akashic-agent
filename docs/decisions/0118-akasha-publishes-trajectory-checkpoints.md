# 0118 · Akasha 按批发布轨迹检查点，可重建性由重放等价守护

- 状态：proposed / implemented for review
- 日期：2026-10-14
- 关联条款：MEM-009、MEM-013、ERR-001
- 勘误：#826 的"同图 t+1 等待 t 的持久发布"收窄为本记录的检查点合同；图与消费进度共同发布、失败不越过前驱不变。

## 背景

Akasha 的状态是消息日志上的折叠：`S(t+1) = F(S(t), E(t), feedback(t))`。日志已经持久，`akasha.db` 是这条轨迹的派生检查点，用于不重放即可恢复与只读查询。

原实现每学一条就发布一次完整检查点：复制旧库、删除并重写全部图表、全库外键校验、整文件摘要。纯算法基准（合成数据，不调模型，5000 轮约 14 MB）中，学一条的 commit 约 136 ms，在线发布约 294 ms，且随历史线性增长；发布占学习持锁时间的大头。

## 决定

1. 在线学习仍逐条 commit，同图只有一个 writer、一个全局顺序；查询仍不学习。
2. 检查点按批发布：一次 `consume` 学完当前已接纳前缀后发布一次，批内最多攒 `PUBLISH_EVERY = 16` 条即发布；关闭时发布剩余尾部。
3. 每个检查点仍是 `(S(k), consumption[:k])` 原子成对发布，必定落在唯一轨迹上；磁盘不会出现有后继而缺前驱的状态。
4. 发布失败沿用原规则：本实例停止同图学习与查询并 fail-loud，重启只装载磁盘上的完整检查点。
5. 未发布的尾部不另存。崩溃后由日志按原序重学，得到与不崩溃时相同的状态；关闭时发布失败只记录，同样留给重学。

## 屏障

性能改动不得削弱的不变量是"在线轨迹 = 日志重放轨迹"，用含消费进度的 `logical_state_sha256` 判定：

- `scripts/akasha_publish_replay_scenario.py`：逐条发布、按批发布并在未发布尾部崩溃后重学、重建式一次发布，三者哈希相同。
- 真实 ledger 与 akasha 插件、确定性 embedding 的全链路运行中，`/akasha_reindex` 同等的重放结果与在线图哈希相同。

## 代价

- 归档与程序化查询读取已发布检查点，最多落后在线状态 15 条，仍是同一轨迹上的有效状态。
- 崩溃后重启需要重学未发布尾部，最多 15 条。

## 不在本决定内

同图学习是顺序折叠，不能并行；查询是 `S(t)` 的纯函数，理论上可以并行，但当前 `retrieve` 会临时改动图对象，且计算受进程内 GIL 限制。查询走不可变快照或独立进程另行决定。
