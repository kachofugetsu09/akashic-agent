# 0150 · 来源只有一个事件入口，删除 EventMail

- 状态：proposed / implemented for review
- 日期：2026-11-11
- 关联条款：PRO-004
- supersedes：0048

## 背景

EventMail 把来源交来的东西分成 Content、Alert、Context 三类，各有独立的提交能力和生命周期：Content 有批次、修订、选择和结算，Alert 有上报、查状态和确认，Context 是可过期、可覆盖的快照。这些区别是为 Wake 的固定流程服务的。

值班（ADR 0149）取代 Wake 之后：

- 值班只需要"发生了一件事"，三类在它眼里是同一种事件。
- 结算和终态没有人再写。日历和 Fitbit 要等告警到达终态才向自己的后端确认，Wake 关闭后它们的待确认队列只增不减。
- Context 每次轮询都写一个信封（生产实测每个来源每小时 12 个），状态有没有变只有来源自己知道，值班没法直接用。
- 一个新来源要接进来，得先在三类里选一个，再实现对应的那套回执。

## 决定

1. 来源的入口只有 `watch.events.v1` 的 `emit` 和工作区的 `watch/sources/*.jsonl`，两者落在同一处、同一种形状。
2. 事件被收下即交付完成。不保留批次、修订、结算、查询投递状态的接口；来源交完就向自己的后端确认。
3. 原来靠"类型"表达的两件事改成事件上的两个可选字段：`key`（来源自己的稳定标识，同一来源同一个 key 只记一次，重试不会重复）和 `state`（这是该来源的当前状态，没变不记新事件）。
4. 删除 `eventmail` 插件及其存储、三类来源端口、选择与结算接口、只为它服务的调试脚本。用户信息入口里的"当前状态"改由值班提供。

## 没有选的做法

- 保留 EventMail 只当一个去重的收件箱：它剩下的职责（收下、去重、按序读出）值班的事件文件已经有了，留着就是两份。
- 在值班里按类型分别处理内容、告警、状态：类型会变成来源的身份标签，之后每加一种来源都要回答"它算哪一类"。紧急与否看内容，不看类型。
- 让值班去比较 Context 快照判断状态变没变：哪些字段算"变了"只有来源知道，放在值班里只能靠猜。

## 已知限制

- `key` 的去重范围是事件的保留期（14 天）。来源在 14 天后重交同一个 key 会被记成新事件；来源自己的游标仍然是第一道防线。
- 没有"事件过期"这个概念。值班积压时，一条"半小时后开会"的事件可能在开会之后才被判断；事件带发生时间，由值班员据此判断。
- 旧的 `eventmail.sqlite3` 留在插件数据目录，不迁移、不自动删除。

## 影响

- 兼容性：仍然绑定 EventMail 来源端口的外部插件在这个版本上会因为缺少依赖而不启动来源部分。订阅、日历、邮件、Fitbit、Steam 的迁移 PR 必须先合并并装到生产，再部署本变更。
- 回滚：恢复上一个版本的 Core 和各来源插件的上一个版本；两边不共享状态。
