# 0114 · 会话已读水位改为服务端共享

- 状态：proposed / implemented for review
- 日期：2026-10-11
- 修订：#1184 的未读状态（"本浏览器记录 head_seq，不引入服务端状态"）。
- 先例：同一 owner 中的 `navigation:pins`（WEBUI-009）。

## 决定与理由

维护者同时用电脑和手机使用 akashic。#1184 把已读水位放在各浏览器 localStorage，
导致两个问题：在电脑读过的回复，手机通知栏的提醒一直不消失；两端侧栏的未读圆点互不同步。
两者缺的是同一个跨设备事实，因此把已读水位移到服务端，复用既有 OwnerStore，不新增表或迁移。

1. **水位。** 每个会话一条 `read:<session_id>` 记录，值为已读到的 seq；只前进，截断到当前 head。
   akashic 是单用户系统，所有设备共享同一水位。
2. **基线。** 首次使用时一次写入 `read-baseline`：已有会话按当时 head 视为已读；之后出现的
   会话（例如主动消息新开的会话）从头算未读。
3. **Web。** "是否在读"的判定沿用 #1184：页面可见、正在看该会话、已加载到某个 seq。
   满足时 `POST /api/chat/sessions/read`；侧栏摘要 WebSocket 帧增加 `read_available` 与 `read`
   （快照加增量），所有设备据此计算未读。服务端不提供水位时退回本地记录。
4. **通知流。** 已读的消息对所有客户端都不再提醒。客户端在请求中声明 `read_events: true`
   后，`ready` 携带当前水位，之后水位前进时推送 `read` 事件，客户端据此撤掉已读提醒。
   旧客户端遇到未知事件会停止接收，因此不声明就不推送。

## 已知限制

- 已读水位只在同一进程内实时唤醒订阅者；通知流按既有 2 秒轮询节奏读取。
- 浏览器原有的本地已读记录不迁移；上线时由基线把已有会话视为已读。

## 验收

`tests/test_read_marks.py` 使用真实 MessageLog 验证基线只写一次、水位只前进、分页读全、
提交后唤醒订阅者；侧栏摘要携带已读快照与增量；通知流跳过已读消息，声明后推送 `read`、
不声明从不推送；标记接口首次建立基线、截断到 head、拒绝不存在或其他通道的会话。
