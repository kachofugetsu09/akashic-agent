# 0151 · 值班：每件事要有着落，来源可以是一个脚本

- 状态：proposed / implemented for review
- 日期：2026-11-11
- 关联条款：PRO-004、PRO-005、PRO-006
- 补充：0149、0150

## 背景

值班上线第一天，主 Agent 被叫醒三轮，只对用户说了一句话。其余几件它自己判断"值得让用户知道"的事，处理方式都是写进便签"等他下次来问再提"：三篇直接接用户主线的论文、一条第二天才有结果的消息、一个只有用户知道的上课时间。便签只有用户主动来聊天时才有机会被带出来，这些事实际上被搁置了。

原因在提示词：叫醒提示词只讲打扰的代价（"不调用，用户什么都不会收到；多数时候这正是合适的选择"），没有讲沉默的代价，也没有要求给搁置的事一个兑现时间。

另外两个问题在排查时暴露出来：

- 主 Agent 给自己写的"到某个时间回来做某事"，值班员会按"条件不成立"或"这类内容嘱托说了不叫醒"直接记为 log，一次性的嘱托随即归档，这件事就丢了。带时间的行写在"留意"一节时根本不会到点查看。
- 用户在对话里说"以后帮我盯着某某"而没有来源覆盖时，主 Agent 没有一个不花模型调用、重启后还在的办法定期检查：服务器上没有 crontab，定时任务工具每次触发都要跑一轮模型。

## 决定

1. **每件事结束前要有着落，只有三种**：现在说；在 `WATCH.md` 里给自己定一个时间回来；放下并从待看和便签里删掉。"等用户下次来问"不算着落。先看时机再选着落：用户睡着、在玩、说过别打扰时，除了等不起的事都走第二种；等不起的事（安全、期限、用户点名要第一时间知道的结果）不看时机。
2. **到点查看**：嘱托写了条件的照旧由值班员对照状态判断；没写条件、或者条件要去查才知道的，直接叫醒主 Agent。带时间的行写在哪一节都到点查看。
3. **脚本来源**：`watch/sources/名字.sh` 或 `名字.py` 由值班每轮运行一次，标准输出的每一行是一条事件，格式与 `名字.jsonl` 的一行相同。脚本经宿主进程服务执行，和主 Agent 的命令行是同一个环境；三十秒没结束就终止；失败本身作为一条事件交回，同一天只记一次。
4. 技能说明写明主 Agent 能做什么、做不到什么，以及"用户让你盯一件事"的步骤：先看有没有来源覆盖，有就只加嘱托，没有就先加来源；用户嫌某类内容吵时改口径，不退订。

## 依据

两套离线评测，被测模型是生产用的主 Agent 模型，断言都是可核对的事实（有没有推送、`WATCH.md` 里有没有新增带时间的行、来源文件和定时是否真的建出来），每条用例重复两到三遍。用例随机分成训练和留出两半，留出集只看分数。

- 被叫醒后的行为（22 条用例）：训练集 60% → 97%，留出集 44% → 94%；每轮平均推送 0.33 条 → 0.47 条。该忍住的场景（用户在玩、睡着、说过别打扰、同一件事已经说过）改动后全部通过。
- 值班员对"到点叫我"的判断（6 条用例各 3 遍）：9/18 → 18/18。
- 主对话里"以后盯着某事"（22 条用例，命令在一次性容器里真实执行）：结果见 PR 描述。

评测脚本和素材含用户的真实记忆与对话，留在本机，不进仓库。

## 已知限制

- 评测里的主 Agent 没有生产的完整系统提示词和长对话历史，分数只说明方向；上线后要看真实的几轮。
- 脚本来源每轮都跑，间隔跟值班间隔走（默认十分钟），不支持单独的周期；想少跑的脚本自己判断。
- 脚本和主 Agent 的命令行权限相同，没有额外的沙箱。
- 推送量会上升。每天叫醒次数的上限（PRO-006）不变，用它兜底。
