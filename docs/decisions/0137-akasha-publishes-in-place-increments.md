# 0137 · Akasha 检查点原地增量发布，随时钟变化的派生列不入库

- 状态：accepted / implemented for review
- 日期：2026-10-29
- 关联条款：MEM-009、MEM-013、ERR-001
- 细化：0118 的「按批发布 `(S(k), consumption[:k])`」不变，本记录只改变一次发布怎样写进磁盘。

## 背景

0118 之后，每 16 轮发布一次，每次仍要：备份复制整库、删除并重写全部边表与 hub 表、全库外键检查、对整个文件算 sha256、重新校验整段消费进度 JSON。线上规模（约 5.9k 轮、2.6 万条边）下，这一套跑一次要几百毫秒，摊到每轮与学习本身同量级，并且随历史线性增长。

全量重写里最大的放大因素是 `effective_weight`。它是由 `weight`、最近支持时间和当前时钟算出来的派生量，时钟每轮都在走，所以每轮所有边的这一列都会变。把它存进库有两个后果：
1. 每次发布都必须重写全部边。
2. 已发布行的内容取决于「什么时候发布」：按批发布与每轮发布写下的 `effective_weight` 不同。只因为这一点，就无法要求在线按批发布与一次性重建逐行相同。

恢复与宿主都不读这一列。

## 决定

1. **schema v3**：`hub_memberships` 与 `temporal_edges` 去掉 `effective_weight`。需要时由同一行的其他列与时钟现算，信息不丢。
2. **原地增量事务**：连续发布直接在已发布库上开一个 `BEGIN IMMEDIATE` 事务，`synchronous = FULL`，用 rollback journal。
   - 追加本批新 turn、反馈、hub、事件、种子与召回记录。
   - 边按持久化列与上次发布的副本逐位比对，只改写变化的边。
   - 时钟、外部 seed（只写变化项）、当前语境与 burst 成员整体改写。
   - 元数据与消费进度在同一事务里写入，提交即 `(S(k), consumption[:k])` 一起前进。
3. **只信自己写下的检查点**：事务开头逐项核对文件正是上次发布的检查点（schema 版本、消费进度原文、配置、容量、边数与 hub 数）。任何一项不符就回滚，退回 0118 的复制加全量重写路径。旧版本 schema 的库同样走全量重写，并就此升到 v3。
4. **只校验新后缀**：消费进度的追加与发布只校验新条目，前缀已在上一次发布时校验过。规范 JSON 由逐条缓存的片段拼接，与 `canonical_json(model_dump)` 逐字节相同。外键在写入时逐行强制。增量路径不再对整文件算 sha256；完整重建仍算并写进回执。
5. **完整重建不变**：仍从空库全量写入，失败不触碰已发布的图。

## 屏障

- `scripts/akasha_publish_replay_scenario.py`：逐条发布、按批发布加崩溃重学、重建式一次发布，三者的逻辑哈希相同。
- 发布中途失败时，文件仍是上一检查点：事务回滚，实例按 0118 停止并 fail-loud，重启后从该检查点重学。
- 线上真实数据（5883 轮）全量重建：与改动前逐表逐位相同（比较时去掉 `effective_weight`，并把 hub 号按创建事件对齐）。

## 代价

- `logical_state_sha256` 的列集合变了，v2 库与 v3 库的哈希不可直接比较。
- 升级后的第一次发布会整库重写一次。
- 增量事务依赖 SQLite 的原子提交；文件必须是本进程上一次写下的检查点。别处改动过的库会被核对出来并走全量重写。
