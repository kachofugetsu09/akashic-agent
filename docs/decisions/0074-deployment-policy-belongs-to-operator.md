# 0074 · 部署者拥有备份、插件映射与迁移选择

- 状态：accepted
- 日期：2026-09-25
- 关联条款：MIG-001、MIG-002、BAK-001、PLG-013、WSP-003
- supersedes：0038 中每次离线发布必须创建恢复点的策略；0021/0066 中既有 selected Root 启动时自动执行缺失迁移的行为。Yoyo 账本与 step 不可变合同保留。

## 背景

停止期发布把全状态备份、按旧 provenance 推断 bundled 更新范围、目标迁移和完整恢复结算绑在一起。
代码更新也要复制业务数据；后续已经部署健康版本时，旧 failed/pending 仍可能阻止部署。
维护者明确要求由部署者判断数据风险和备份，不为低概率恢复场景叠加大量代码。

## 决定

1. 部署者指定 Core commit；可选清单显式列出插件目标与允许执行的 migration ID。不推断升级范围。
   无清单只更新 Core/Bridge；未列出的插件保留原输入及顺序，初装 profile 不参与升级选择。
2. `--backup` 默认关闭，选择后才创建停止期 state/env 备份及发生变化的 unit/CLI 备份。
   备份质量仍受 BAK-001 约束；工具不自动选择、恢复或删除备份。
3. 既有 Root 的普通启动只检查迁移；部署只执行清单批准的 pending step。首次显式初始化仍允许建库。
   已发布 step 不改写，其内部必要恢复机制不等于每次 release 必须全状态备份。
4. 工具保留精确产物、在线只读预检、停止期 maintenance/publication 锁、正式 installer、一次完整 Root CAS、
   实际 Core/Bridge 身份与选中 Fiber 验收。安装提交、Root 提交和运行成功是不同事实。
5. 失败保留阶段、实际发布结果和原错误，不自动恢复旧 runtime/env，不声称回滚业务状态或外部效果。
   `resume` 只重试仍匹配已记录发布结果的启动/验收；结果未知由部署者核对现场后重写计划。
6. 删除全量恢复比对和历史 failure 永久门禁。旧证据原样保留，新发布依据当前 Root/cache/ledger 与真实
   owner 状态判断；未结算的安装或 reload owner 不能由手写成功声明绕过。

## 取舍与验收

不加入自动备份策略、自动 schema 风险推断、通用数据降级或全阶段自动恢复状态机。
代价是部署者必须判断迁移与旧代码兼容性，并在发布结果未知时承担人工检查。
框架仍负责失败明确、身份一致、串行提交及不把局部结果伪装成整体成功。

验收使用既有概念基线、静态检查与临时真实 Git/插件安装/Yoyo/SQLite 场景，不新增单元测试。
Docker/systemd 的完整升级与业务验收须在部署时单独完成，本地场景不能替代生产证明。
操作命令与恢复范围由[部署操作手册](../design/operator-deployment.md)拥有。
