# 0065 · 边界检查不授予 Core 归属

- 状态：accepted
- 日期：2026-09-12
- 关联条款：PLG-014、PLG-016、STA-001、CAP-001、GOV-003、TST-003
- supersedes：[0064](0064-plugin-boundary-is-machine-enforced.md)

## 背景与勘误

维护者确认目标是插件基座、原子能力及其窄合同，业务由无特权插件装配产生。
#593/#594 保留并完善；#595 停止当前迁移路线，保留提交供参考，不合并。

0064 把静态 import 数量与架构完成混同，且存在以下过强结论：

- ServiceKey 按名相等，不代表移动类型、实现或生命周期是零风险文本操作。
- 角色表未被 Runtime 消费；登记不代表能力可加载、可替换或应留在 Core。
- FreshPluginImporter 有 generation 模块身份，但不是任意 Python import 的安全沙箱。
- 静态门不等价于独立包发布和实际安装测试；名字检查也不能证明全部文档正确。
- 共享合同不必全部由 Core 拥有。把业务分支、store 或 snapshot 转导出到允许路径仍是耦合。

0064 保留为历史推理，本记录取代其机械迁移与目标归属判断。

## 决定

1. 保留 import 欠账门，修补包入口、相对导入及自身绝对导入漏报。
   历史迁移纳入精确欠账，不按目录豁免；标准库不误判为 Core 私有模块。
2. 比较目标分支的真实源码。新增依赖不能通过重写账本放行；账本输出命令只读。
   新增公开模块须显式评审，不继续给整个目录中的未来文件自动放行。
3. 角色表只作 Core 文件内字面声明的现状清单。`core` 表示当前提供位置，
   不承诺永久归属；`seam` 不代替可替换性证据；默认 `bundle` 没有额外权限。
4. Core 合同只承载自身事实与机制的必要协议。普通插件可以拥有领域协作合同，
   通过明确能力依赖协作，不能导入其他插件实现。通用原子能力可以有状态和 I/O，
   但值合同不得借此收容服务实现；是否属于 Core 由真实 owner 决定。
5. #594 的删除继续逐项举证。后续先验证完整切片的外置、新增、替换及生命周期，
   不先批量冻结所有业务接口，也不以 import 归零代替成功。

## 理由与取舍

保留可重复静态门可以阻止常见回归，但 Python 的动态性决定它不能证明任意运行时行为。
把局限写清并补真实装配验收，比扩张正则规则或中央业务合同更接近目标。
冻结既有公开模块是过渡兼容措施，不证明这些模块已经足够窄；后续允许有证据地收缩。
不引入新的运行时注册机制，不改变已有 Message、Tool、模型或业务流程。

## 验收、影响与恢复

用户可判断的最终标准与阶段证据见[设计 §7](../design/plugin-boundary-foundation.md#7-验收标准)。
基线比较必须能拒绝“新增 import 并同时加入账本”的变异。
外部插件的新增与替换不得要求 Core 认识新业务名称，缺依赖必须显式失败。

本次不改变持久数据的增加、原位更新、逻辑失效或物理减少协议，不触及正式 workspace。
原 PR 分支和提交保留；代码可按新提交回退，不能据此宣称运行数据或外部效果已经回滚。
