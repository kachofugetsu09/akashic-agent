# 0138 · Akasha 的 dense 打分固定单线程 BLAS，学习检索不算模式补全

- 状态：accepted / implemented for review
- 日期：2026-10-29
- 关联条款：MEM-009、MEM-013、ERR-001
- 细化：0118 的屏障「在线轨迹 = 日志重放轨迹」扩展到跨机器、跨线程数。

## 背景

用线上快照（5883 轮）验证在线与重建是否一致：当前 main 从日志全量重建出的图，与线上的图并不相同。前 558 个事件相同，从第 559 个开始出现末位差异，之后逐渐累积，最终 hub 数也不同。原因有两个：

1. **OpenBLAS 的结果随线程数变化。** 同一个 float32 矩阵乘向量，本机 1 线程、8 线程、16 线程算出三种不同结果。线程数相同时，AMD Ryzen 7 2700（生产）与 Intel Core Ultra 5 125H（本机）逐位相同。生产容器默认 16 线程，所以图其实是「机器核数」的函数：换一台核数不同的机器重建，就得不到同一张图。
2. **#816（2026-09-29）的 `_dense_product` 分块**只在单线程下与原来逐位相同，16 线程下不同。线上图由 9 月 18 日的一次重建加上之后的在线学习构成，因此混合了分块前后两种算法。

另外，学习时的检索还会算一遍完整的模式补全，约占学习一半的时间。但学习只用 evidence 与 diffusion，补全只写进 `recall_runs` / `recall_items`。这两张表不在逻辑状态里，main 上也没有产品读者了（面板读这两张表的部分已经退役）。

## 决定

1. **akasha 引擎加载时，把进程内 BLAS 永久固定为单线程**（`threadpoolctl.threadpool_limits(1, user_api="blas")`）。
   - 不用「临时限制再恢复」：查询与多张图的学习在不同线程并发，恢复会改掉别的线程正在用的线程数。
   - 代价：同进程其他组件的 BLAS 也变成单线程；目前没有其他重度 BLAS 用户。
2. **图元数据记录 `dense_threads = 1`**。新增迁移 `20261029_01_replay_with_single_thread_dense`：凡是不是 schema v3、或没有这条记录的图，先备份，再登记一次性全量重放；实际重放仍由插件的唯一实现 `rebuild_now` 完成，期间停止该图的在线学习。
3. **学习检索默认不算模式补全**（`commit(record_recall=False)`）。记忆状态与查询逐位不变：800 轮对照中，两者的状态摘要与期间每次查询的结果都相同。需要记录补全的工具可以显式打开。
4. **dense / BM25 分数与尾部惊奇度做精确记忆化。**
   - 向量矩阵和倒排都只追加，`(end, cue)` 的分数是纯函数。
   - 同一状态版本上，查询与随后同一轮的学习检索直接共用；返回只读数组，任何原地写都会报错。
   - dense 分块改为 64 行，1 线程与 16 线程下都与 256 行逐位相同。

## 屏障

- 线上快照全量重建：本系列改动前后逐表逐位相同，1 线程与 16 线程各验证一次。比较时去掉 `effective_weight`，并把 hub 号按创建事件对齐。
- `scripts/akasha_publish_replay_scenario.py`：三条路径的哈希相同。
- 跨机器：同线程数下 BLAS 结果逐位相同，有实测。

## 代价

- 部署后要做一次全量重放。改动后的图与改动前的线上图不逐位相同，但它是日志的确定函数。
- 线上图今后不再写 `recall_runs` / `recall_items`；全量重放之后这两张表为空。
- 若部署到 CPU 指令集差异很大的机器（例如 OpenBLAS 选到 AVX-512 内核），单线程结果也可能变化，届时需要再做一次重放，或改用自有的确定性点积。
