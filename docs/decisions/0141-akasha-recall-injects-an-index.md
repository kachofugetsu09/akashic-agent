# 0141 · Akasha 自动召回只注入索引，原文用 fetch_messages 按需读取

- 状态：accepted / implemented for review
- 日期：2026-11-05
- 关联条款：MEM-009、MEM-013
- 细化：0052 的「Akasha 召回进入末尾的临时提醒」。

## 背景

#563 把 Akasha 迁进 Message runtime 时，召回改成了逐条贴出消息全文，每轮最多 12000 字。提醒按输入回放、留在上下文里直到压缩，同一批消息又会在后续轮次反复命中，于是越聊越重：

- 生产「llm学习」会话 41 轮召回共注入 40.8 万字，每轮约 1 万字，命中的全是本会话、仍在窗口里的内容。
- 主会话 464 轮里，排前三的三条消息各被注入了 457 次。

更早的设计是「日期 + 短预览 + 可回源引用」的渐进式暴露。

## 决定

1. **召回数量不变，每条变轻。** 两条通道照旧，自动召回上限仍是 40，不加分数门槛，由模型自己挑。每条消息一行：`- [时间 · dense|completion] 开头 80 字预览（ref=<message_id>）`。不带作者、字数、分数。
2. **当前未压缩窗口里已经出现的消息不再注入。** 包括窗口本身的消息、窗口内各轮自动召回与 `recall_memory` 呈现过的消息、`fetch_messages` 读过原文的消息。压缩后它们不在窗口里，可以再次出现。
3. **排除在首次查询时决定，结果写进召回记录的 `presented_message_ids`。** 同一输入的工具续步和重启后的重渲染只渲染记录里那几条，提醒文本不变，前缀缓存和 `recall_memory` 的出处核对都不受影响。
4. **新增 `fetch_messages(message_ids)` 读原文。**
   - 返回时间、作者和全文，一次最多 20 条、共 30000 字。
   - 只认调用会话可读的那张学习图里学过的消息，以及本会话自己的消息；独立项目图里的、未学习或已跳过的消息读不到。
   - 消息所属会话从已发布的消费出处反查，ref 只需 message_id。
5. `recall_memory` 的结果用同样的索引格式。

## 屏障

- 生产召回记录离线重放：主会话平均每轮由 11298 字降到 1275 字；「llm学习」由每轮约 1 万字降到 0。
- 真实插件运行时验收：跨会话召回出索引行；同窗口第二轮不再注入且重渲染一致；窗口只剩最新输入时历史重新出现；`fetch_messages` 读到原文，独立项目和不存在的 ref 都被拒绝。

## 代价

- 部署时正在进行中的那一轮，会按新格式重渲染一次，提醒文本变化导致一次缓存未命中。
- 升级前用随机身份保存的旧召回记录不参与窗口排除。
- 模型需要细节时要多一次 `fetch_messages` 调用。
