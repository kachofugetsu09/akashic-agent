# 0105 · Ledger 插件拥有业务持久化

- 状态：proposed / implemented for review
- 日期：2026-10-11
- 依据：#1179 边界③；用户授权自主决定，并将重大决定单独提交评审。

## 决定与理由

Ledger 是显式选择的普通插件。它打开并关闭 `sessions.db` 的消息、附件元数据、
身份、接纳和入站交接连接，提供 reader、writer、同库 owner 事务及附件窄端口。
Core 不构造这些对象，不发布占位服务，也不保留旧模块转发壳。
公共消息值和持久化端口归入 Ledger contract；传输值归入 Channels contract。
消费者只依赖公开合同，公共 API 制品和运行 generation 继续采用不同生命周期。

│ Core 选择、组合、Effect │───►│ Ledger generation          │
└────────────────────────┘    │ 消息库、附件、身份、交接   │
                              └──────────────┬─────────────┘
                                             │ 窄端口
                              ┌──────────────▼─────────────┐
                              │ Channels / Sources / UI 等 │
                              └────────────────────────────┘

关闭依赖图先等待消费者收束，Ledger 再关闭入站租约和数据库连接。Channels 的每个
新连接开放接纳后重放自己能够处理的持久交接；不再依赖 Core 启动末尾的一次回调。
因此在启动后安装或重启 Channels，也能恢复保留的输入。重放仍使用原消息 ID 和
原 owner 的事务去重，不制造第二条消息，也不承诺外部效果可以随 SQLite 回滚。

## 历史迁移与数据

五项既有消息迁移移入 Ledger 的离线 Yoyo bundle。ID、依赖、事务设置和 SQL 保持
原行为；历史实现只依赖 bundle 内冻结的 schema helper，不导入运行插件。
`migrations/ledger-moves.toml` 保存准确的新旧路径与 SHA-256，门禁同时校验两端。
迁移账本中已完成或空库基线声明的依赖可解析，但 receipt 不能被当成步骤执行。
Core-only 迁移必须先运行它依赖的实际插件步骤，不能跨过尚未落账的依赖。

消息和 owner 记录的权威表、附件目录、身份和交接格式不变。本次不复制、重建、
清理或删除业务数据；仅旧 generation 的瞬时接纳租约在新 Ledger 激活时清除，
持久交接按原成功结算协议减少。卸载 Ledger 保留数据库和附件。
默认发行配置显式启用 Ledger；最小组合不启用时，不创建 `sessions.db`。

消费者必须在同一层切换，否则中间态需要 Core 业务依赖或第二套类型身份。
