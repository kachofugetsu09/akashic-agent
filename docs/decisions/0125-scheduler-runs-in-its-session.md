# 0125 · 定时任务在创建它的会话里执行

- 状态：proposed / implemented for review
- 日期：2026-10-18
- 关联条款：SCH-003、MEM-001～MEM-002
- supersedes：0058 的“每次触发一个独立内部 Session”

## 背景

0058 让每次触发在独立内部 Session 里跑 ReAct，再把最终回复的文字和附件引用抄一份发到目标会话。线上暴露三个问题：

- 工具结果（例如 `render_visual` 的天气卡）留在内部 Session，从来没有送到用户面前；只有模型最终回复里的附件会被抄过去。
- 过程对用户不可见，用户也不能在原会话里追问“刚才那条是怎么查的”。
- 为了把内部 Session 和通知分开，Scheduler 自己维护了一套搬运、提前触发（P90 延迟估算）和选模型逻辑。

参照 Memoh：它的定时任务就是一轮普通对话，跑在新建或固定的会话里；会话忙时直接丢弃，定时轮次会进入记忆抽取，模型不跟随会话。我们取它“在哪里跑就在哪里显示”，不取丢弃和记忆部分。

## 决定

1. 每个任务属于创建它的会话（`schedule` 工具从调用来源取得会话与投递渠道，模型不再填 `channel/chat_id`）。
2. 到点后经 `CONVERSATION_COMPLETE` 在该会话里执行，与 subagent 回报父会话同一条路：主对话空闲才开始；用户插话时先让用户的回复运行，之后从同一 Input 与已结算工具继续。
3. 每次触发独占来源 `scheduler:<fire_key>`。Input、工具调用、工具结果和最终回复都写在目标会话里，用户能看到过程，工具产出的卡片在原处渲染。
4. 任务两种动作：`notify` 到点原文推送，不调用模型；`run` 跑一轮回复。删除 `instant/soft` 与提前触发。
5. `run` 的历史范围由任务决定，默认 `none`：
   - `none`：模型请求只由本次触发来源的消息组成，不带会话摘要，也不触发整会话压缩；天气、新闻这类独立任务用它。
   - `session`：带上会话历史，与普通对话相同。
   范围只作用于请求组装（`REPLY_EXECUTE` 的 `history="own"`）；读面、提交、竞争检查和恢复仍使用整个会话的真实日志。
6. 任何回复的请求都不带其他来源仍在进行的轮次（该来源最后一次结束之后的消息；`failure`/`abandon` 也算结束）。用户在任务一批工具中途插话时，对话请求里不会出现未配对的调用；任务结束后，对话就能看到完整过程。此时压缩只覆盖第一条被隐藏消息之前的部分，保证摘要范围在真实日志和请求里都连续；容量估算和原文尾部仍按完整请求视图计算，当前输入和本来源进行中的消息照常保留（#1544：曾把整个快照截到该位置，当前输入随之丢失，回复报“保留输入必须是当前来源的真实 Input”）。
7. 模型跟随会话当前选择；工具与会话一致，只去掉 `memorize`、`remember_memory`、`forget_memory`。任务里调用 `schedule` 创建后续任务时，目标沿用本次触发的会话与渠道。
8. 最终回复是本次来源最后一条结束的 Output，Delivery 直接投递这条原消息，不再复制通知。
9. 模型失败耗尽既有恢复后，在同一来源追加 `failure` 控制记录，并将本次触发结算为失败。记录已保存、触发尚未结算时重启，只补结算，不重新调用模型；磁盘或程序错误仍暴露原异常。

```text
到点 ─▶ CONVERSATION_COMPLETE(目标会话)        用户插话：先回用户，再接着跑
          │
          ├─ Input  scheduler-input:<key>     source = scheduler:<key>
          ├─ 回复程序（history = none | session）
          │    工具调用 / 结果 / 卡片都在目标会话里
          └─ 最终 Output ─▶ Delivery 原消息投递 ─▶ 结算 fire
```

## 记忆

定时任务不会写脏长期记忆，依据都是现有机制：

- akasha 与 markdown_memory 只把配置里列出的来源（默认 `conversation`、`programmatic`、`legacy-unattributed`）当作学习样本，`scheduler:*` 不在其中。markdown_memory 核对摘要覆盖范围时会读完整快照，但只抽取允许来源。
- 兴趣原型只用 `conversation` 的完整轮次。
- 任务里关闭三个写记忆工具；`recall_memory` 只读，保留。
- 用户之后在对话里提到任务结果，是用户真实说过的话，照常学习。

新增记忆插件必须同样按来源白名单学习，默认只含对话来源。本次不在宿主层另建“可学习来源”注册表。

## 已知限制

- `none` 不压缩：单次任务超出上下文时明确报错结束，不截断。
- 用户取消执行中的任务时，Scheduler 等原执行排空后为未结束轮次追加现有 `abandon` 控制记录；未执行的工具不重跑，原消息与工具回执保留，后续对话和压缩可以继续。重启后从持久取消状态补齐同一条记录。
- 普通对话之后会看到会话里的任务过程（与 subagent 回报相同）。若嫌占上下文，再单独设计“其他来源对对话只公开结论”。
- 用户插话时，若任务的工具正在执行，用户的回复要等这次工具结束后才开始（与其他来源排空工具的规则一致）。
- 目标会话不存在时 `run` 直接以失败结算；`notify` 照旧写入。

## 验收

`scripts/scheduler_tools_scenario.py`（真实插件栈，本地 HTTP 模型）：

- 任务消息写在目标会话，来源独占；`none` 的请求里没有会话历史，`session` 的请求里有。
- 任务一批两个工具执行中用户发消息：先完成当前工具，回复用户（请求里不含进行中的任务），再继续任务；两边都完成，投递各一次。
- 一批工具执行中取消任务：旧记录保持不变，轮次以 `abandon` 结束，后续用户输入仍正常回复。
- 模型上下文超限：保存真实失败原因并结算；已有失败记录的 pending 触发恢复时不再调用模型。
- 任务里调用 `schedule` 创建原文提醒，提醒写入同一会话并送达。
- 旧流程已开始未发布的 pending 触发以失败结算，不发模型请求、不重复写 Input。
- 晚注册、并发固定目录、卸载、禁用工具拒绝保持原行为。

`scripts/timer_plugin_scenario.py`：`notify` 的取消、重启、换代与送达。
