# 项目文档写作规则

## 1. 先判断内容属于哪份文档

| 内容 | 写入位置 |
|---|---|
| 新会话入口、按任务阅读顺序、文档导航 | `INDEX.md` |
| 从接手任务到提交评审的固定执行顺序 | `WORKFLOW.md` |
| 长期需求、禁止事项、语义不变量 | `projectneed.md` |
| 当前仍未完成的工作、阻塞、接手点 | `NOW.md` |
| 已经作出的重要选择、理由、替代方案、勘误 | `decisions/` |
| 单个问题的架构、调用链、迁移步骤和验收设计 | `design/` |
| coding agent 的开工、核对、实现和交付纪律 | `WORKFLOW.md`；本地 agent 指令由运行环境提供，不进入仓库 |
| 可复制的任务合同、变更声明、决策和 context handoff 骨架 | `templates/` |
| 当前实现细节 | 代码、类型、测试和就近注释 |

一个事实只设一个权威位置。其他文档使用条款 ID 或相对链接引用，不复制整段内容。

`INDEX.md` 只维护路径、顺序和选择条件。新增、移动、改名或废弃项目文档时同步更新索引；不得把需求正文复制到索引里。

## 2. `projectneed.md` 只写稳定语义

- 每条需求使用稳定 ID，能在 PR、对话和测试名中准确引用。
- 先写可观察结果，再写禁止路径；不把某个当前类名或文件行号当成永久需求。
- 不记录测试成功数量、临时基线提交、一次性进度、会话转录、模型思考过程和生成说明。
- 需求必须说清受保护状态、允许变化和失败语义。只写“要安全”“要稳定”“避免丢失”不算完整条款。
- 当前实现与需求不一致时，文档写目标语义；差距放进 `NOW.md`，证据和迁移放进技术设计。

## 3. 决策记录保留推理历史

- 文件名使用 `NNNN-short-title.md`，编号只增不改。
- 状态使用 `proposed`、`accepted`、`superseded` 或 `rejected`。
- 每条记录包含背景、决定、理由、影响、验收和关联条款。
- 决策错误时不删除原文件。新建记录说明勘误，并在双方写明 `supersedes` / `superseded by`。
- 决策记录不充当待办。尚未完成的实施步骤另写到 `NOW.md`。

## 4. `NOW.md` 维持高信息密度

- 只保留未完成、正在做或真实阻塞的事项。
- 每项说明期望结果和验收边界，不写流水账。
- 一项工作完成后立即删除。Git、PR 和决策记录负责历史回溯。
- 不创建“Done”章节，不累积周报，不把长期愿望混进当前热点。
- 当前任务的逐步计划留在会话状态或 handoff。只有任务结束后仍存在、维护者已经接受且可以继续接手的工作才进入 `NOW.md`。

## 5. `WORKFLOW.md` 只保存执行顺序

- 它回答开发者按什么顺序读取、隔离、声明、实现、验证、核对和交付。
- 具体产品语义只由 `projectneed.md` 定义，工作流使用条款 ID 引用。
- Gate 的参数和报告格式引用 `docker/debug/README.md`，工作流只保留稳定入口和状态判断。
- 新增阶段或交付字段时同步检查 `INDEX.md`、PR 模板和工作流契约测试。

## 6. 技术设计从真实证据出发

技术设计至少包含：

1. 问题和用户意图。
2. 当前真实调用链和状态 owner。
3. 已确认事实、推断和未知边界。
4. 目标结构和权限边界。
5. 失败、取消、并发、迁移和回滚。
6. 分阶段实施方案。
7. 能独立判断成败的验收标准。

涉及 UI/UX 或架构时，使用 Unicode box-drawing 绘制纯文本图。图只表达关键关系，不复制代码目录树。

涉及持久状态时，不能只列路径、表名和 owner。每个对象至少写明：正常增加路径、允许的原位更新、逻辑失效方式、物理删除条件、授权者和恢复证据。没有减少协议就明确写“当前不得自动减少”，不要把代码里存在 `DELETE` 方法写成产品允许自动删除。

## 7. 中文表达

- 默认使用平实、准确的技术中文。先写谁做什么、改变哪个对象、产生什么结果。
- 主语和谓语必须匹配真实动作。数据库可以“保存记录”，不能“理解意图”；测试可以“发现差异”，不能“保证永远正确”。
- 抽象词后面要落到具体对象。写“语义边界”时说明是哪类状态、哪个调用者和哪种写入。
- 一句话只承担一个主要判断。复杂因果拆成短段，列表用于稳定映射和验收项。
- 不用宣传口号、金句式转折、假口语和空泛收益代替事实。
- 规范条款可以使用“必须”“不得”；说明段落避免连续堆叠否定句，优先写目标动作。

## 8. 引用与证据

- 代码证据优先引用符号和相对路径；行号只用于当次审查，不作为长期锚点。
- PR、commit 和事故数据写入技术设计或决策记录，不反复复制到需求条款。
- 来自旧会话、记忆或历史文档的结论必须标明来源，并用当前实现复核。
- 未验证的信息写成未知边界，不能补一个看似合理的事实。

## 9. 修改联动

| 发生的变化 | 必须检查的文档 |
|---|---|
| 新增、移动、改名或废弃工作手册文件 | `INDEX.md`、所有入站链接 |
| 开工、验证或交付顺序改变 | `WORKFLOW.md`、`INDEX.md`、PR 模板、工作流契约测试 |
| 用户可见语义或数据保留规则改变 | `projectneed.md`、相关决策、semantic tests |
| 架构 owner、权限边界或提交协议改变 | 新建或更新决策、相关设计 |
| 新增尚未完成的实施事项 | `NOW.md` |
| 工作完成 | 从 `NOW.md` 删除 |
| agent 协作纪律改变 | `WORKFLOW.md`；运行环境专属规则留在本地 agent 指令中 |
| 只改内部实现且语义不变 | 通常只改代码和测试，不扩写需求 |

文档和实现出现冲突时先暴露冲突。不得使用模糊措辞让两边看起来都对。
