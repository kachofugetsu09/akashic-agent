# 设置用量页热读取

## 问题与合同

基线 `8b0f0afa` 的设置「用量」每次挂载都会把 Token 数据清空。
线上只读筛选在 Chromium、1440×900、800ms 延迟 / 1Mbps 下测得三次重开中位数 1346ms；
同轮模型、插件、新手引导的已读内容约 63ms。该筛选不是候选 A/B。

候选按 ADR-0127 为今天、7 天、30 天各保留一个模块资源。只复用相同本地日期范围的
完整结果，后台仍读真实 API；扫描未完成时保留该范围上次的完整结果，继续扫描只由可见页面驱动。
不同范围的迟到回包不改当前页，失败保留内容并说明未能更新。三个资源不预热、不写浏览器存储。
回包相同则复用对象，不重建图表。Token 进度与错误使用自己的节点，避免写进隐藏的额度区。

这里测的是 Token 与缓存区域。上方订阅额度仍沿原读取路径；首次读取、全页启动、
生产候选、移动端和全部交互的 300ms 目标不由这组结果证明。

## 重放

两套独立 worktree 分别构建基线和候选，使用相同 lock 文件、浏览器与固定数据。
基线也复制本 PR 的 `serve-startup-runtime.py` 到相同位置，仅统一测试启动器；旧版没有 `--usage-records` 参数。
各自启动下面的真实 Runtime，`--state` 必须是不存在的新目录；端口分别为 24688 / 24691：

```sh
npm run build
python scripts/webui-performance/serve-startup-runtime.py \
  --state /tmp/usage-baseline --port 24688 --usage-records 60
```

60 条是明确标为 benchmark 的合成用量记录，通过 ModelsStore 与 MessageLog 写入一次性状态，
不调用外部模型。真实 HTTP 聚合后为输入 77700、命中 18000、输出 3000、调用 60，分到 12 个模型。
退出 Runtime 时核对全部消息行；测试不会写正式 workspace。

```sh
node scripts/webui-performance/measure-usage-settings.mjs \
  --baseline http://127.0.0.1:24688 --candidate http://127.0.0.1:24691 \
  --runs 7 --output /tmp/usage-paired
node scripts/webui-performance/verify-usage-settings.mjs \
  http://127.0.0.1:24691 /tmp/usage-behavior
```

测量先从真实 API 完整读完三个范围，再计时重开和切换。完成要求选中范围正确、
四项指标存在、图表桶数正确、全部内容与该范围已读值一致，并经过两帧；后台回包另计时、
校验 HTTP 成功与 complete，之后再次核对完整内容。基线与候选按 AB/BA 交替，网络顺序轮换，
CPU×1/×4 分开统计。网络为 LAN 20ms / 100Mbps，弱网 800ms / 1Mbps，无丢包。
所有失败保留并导致非零退出；脚本、lock、浏览器版本、响应 hash 与截图随报告保存。
`freshMs` 是响应正文接收完成时间，不是更新后的最终绘制时间。
